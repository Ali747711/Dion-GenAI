# Contract deviations and clarifications

Tracked per the backend brief: "If you must deviate, write the deviation here." Everything below is a clarification of an ambiguity in `API_CONTRACT.md`, not an intentional break from it. None of these change response field names/types.

1. **List envelope applied uniformly.** The contract's Conventions section defines lists generically as `{ data: T[], nextCursor: string | null }`. `GET /capabilities` and `GET /projects` are documented as returning "a list of X" but their endpoint rows don't show `cursor`/`limit` query params. I applied the same `{ data, nextCursor }` envelope to them for consistency (`nextCursor` is always `null` there, since they aren't cursor-paginated). If the frontend expects a bare array for these two, that's a one-line change in `capability.controller.ts` / `project.controller.ts`.

2. **`DELETE /api/v1/session` requires an existing session.** The contract's auth-exemption line names only "GET/POST /session" as not requiring authentication; I read that literally, so logging out without a session returns `401 UNAUTHENTICATED` rather than a no-op `200`. Trivial to relax if the frontend expects logout to always succeed.

3. **`POST /usage/reconciliations` body `source` vs. `LedgerEntry.source`.** The request body's `source` field is a free-text string (e.g. `"manual check on Noiz dashboard"`), while `LedgerEntry.source` is the fixed enum `'owner' | 'app' | 'provider' | 'reconciliation'`. The created ledger entry sets `source: 'reconciliation'` (the enum) and folds the request's `reason` and `source` strings into the entry's `note` field as `"${reason} (reported source: ${source})"`.

4. **Idempotency conflict on a changed payload.** The contract says "same key+owner returns the existing job (200)" but doesn't state what happens if the same `idempotencyKey` is reused with a *different* payload. Per the PRD/todos ("changed payload with same key conflicts"), this returns `409 CONFLICT`.

5. **Stored asset MIME type is fixed at `audio/mpeg`.** Both the mock provider and the (unverified) live adapter currently ingest results as `audio/mpeg` rather than sniffing the real content type/signature. This is accurate for the mock provider (the sample file is an mp3), but before enabling `NOIZ_MODE=live` for real, `ingestResult` in `src/worker/jobProcessor.ts` should detect the actual content type from the provider's response instead of assuming mp3.

6. **Live Noiz response shape is inferred, not verified.** `src/services/provider/live.provider.ts` implements the documented pieces (base URL, bearer-less `Authorization` header, multipart `POST /text-to-music`, `GET /text-to-music/{id}`, and the "business code non-zero under HTTP 200 is an error" rule) but the exact JSON field names for variant IDs, poll status, and result URL are not verified — `LiveNoizProvider` accepts a couple of plausible key names per field (e.g. `gen_product_id` or `id`; `status` or `state`; `audio_url`, `result_url`, or `url`) and throws a clear `ProviderTransientError` if the shape doesn't match anything expected, rather than guessing silently. It is exercised only via unit tests with a mocked `fetch` (`tests/provider.live.test.ts`) — never against the real API.

7. **Rate limit thresholds.** The contract requires rate limiting on login and job creation but doesn't specify numbers. Chosen: login 10 requests / 15 min per IP; job creation 20 requests / min per IP (`src/middlewares/rateLimit.middleware.ts`).

8. **Session id regenerates on login.** Not specified by the contract; done to prevent session fixation. The cookie name, CSRF flow, and response shape are unchanged.

## R2 — Audio Studio deviations and clarifications

9. **Validation field-path prefixing preserved.** R1 validated `POST /jobs`'s `input` as a nested Zod field, so a validation error reports e.g. `fields: { "input.lyrics": "..." }`. R2 validates the kind-specific input schema separately (dispatched by `kind`), so a new helper (`parseNestedOrThrow`) re-prefixes issue paths with `"input."` to keep the exact same field-key shape for every kind. No client-visible change.

10. **`maxConcurrentPaidJobs` in `GET/PATCH /budget` still reports `1`, but concurrency is now enforced per billing group.** The contract's R2 section says "at most 1 in-flight job per billing group (`credits`, `usd`)" — i.e. up to 2 jobs can be in flight at once (one credits job + one usd job), not 1 globally. The `maxConcurrentPaidJobs` field's meaning/value is unchanged from R1 (it still describes the credits-group limit) since the contract only says R2 "adds `usdMonthlyCap`" to `Budget`, not a new field for the usd-group limit. `POST /jobs` enforces the real per-group rule regardless of what this field reports.

11. **Sound/speech settlement uses the actual provider-reported/generated duration, not the requested one.** `NOIZ_R2_CONTRACTS.md`'s "$0.001/s" wording for `/text-to-sound` doesn't say requested-vs-actual explicitly. We settle on the real duration (mock: the WAV's exact generated length; live: the `X-Audio-Duration` response header), falling back to the requested duration only if the provider's reported duration is `0`/unavailable (the documented JSON-fallback drift path for `/text-to-sound`, section 7.1). Speech's charge is char-count-based (no duration variance), so this only affects `sound`.

12. **Mock provider always returns WAV for `sound`/`speech`, regardless of the requested `format`.** Per the brief ("sound/speech return a generated WAV... pure-JS WAV writer is fine"), the mock never encodes mp3. The stored asset's MIME type is still independently detected from the real bytes (always `audio/wav` in mock mode), so no format is ever mislabeled — it's just that mock mode can't currently honor an mp3 request. Live mode requests the client's chosen format from Noiz directly.

13. **Live cover result download reuses the same (pre-existing, unverified) local-path assumption R1's music adapter already had.** `ingestAudioFromLocalPath` (used by both `music` and `cover`) copies from `result.resultLocation`, which works for the mock provider (a local file) but was never wired to download a *remote* `audio_url` for live mode — this gap already existed for R1 music (see note 6 above) and is unchanged/extended to cover, since neither was ever exercised against the real API. The one place a live URL-vs-binary download *is* implemented end-to-end is `/text-to-sound`'s documented JSON-fallback path, via the new safe-fetch downloader (`src/services/safeFetch.service.ts`), because the brief specifically called that out.

14. **Mock `voice_clone` fabricates a preview audio file; the documented live response does not include one.** `NOIZ_R2_CONTRACTS.md` §1.2 shows the clone endpoint's JSON response has no audio bytes, so `LiveNoizProvider.cloneVoice` always returns `previewBuffer: null` (the voice's `previewUrl` stays `null` until some future sync mechanism, out of scope here). The mock provider generates a short synthetic preview for a nicer smoke-test/demo experience — this is intentionally richer than the live contract, not a live-parity claim.

15. **Real MIME detection (fixing R1's hard-coded `audio/mpeg`).** All ingestion paths (`music`, `cover`, `sound`, `speech`, `voice_design` previews, `voice_clone` preview) now sniff the real magic bytes (`src/libs/utils/audioSniff.ts`) and store the detected type, falling back to a sensible default (`audio/mpeg` for music/cover, `audio/wav` for the rest) only when sniffing fails — which in practice only happens for the test suite's synthetic non-audio fixture bytes, never for the real sample file or generated WAVs.
